# MandatePay — A Company Card for AI Agents
> A company card for AI agents: rules in plain English, spending in bounds, every dollar audited.
PayPal AI Hackathon 2026 · Submission deadline: 2026-11-13 04:00 Beijing time
Today an AI can write code, send email, and book meetings — but nobody grants an AI payment authority, because the money is gone if it goes wrong. MandatePay gives an AI agent a spending cage: the user states constraints in plain English (monthly budget, vendor allowlist, per-transaction threshold), and the agent executes purchases inside those bounds. Every transaction produces a three-layer Mandate record (Intent → Cart → Payment) that can be audited line by line.
The pitch in one line: everyone else is building *"an AI that buys things."* We are building *"an AI that is allowed to buy things."*

Why the agent stops and asks


When the agent places an order, PayPal returns `PAYER_ACTION_REQUIRED` and an `approval_url`. A human has to open that URL and approve the payment before it can be captured.
This is not a bug. It is the product.
1. MandatePay's entire premise is *"the AI must not spend money behind your back."* Fully automatic capture contradicts that premise directly. 2. PayPal's own agentic-commerce model is *"a human pre-authorises a scope; the agent acts inside it"* — not *"the agent has the card."* 3. Judges evaluate the safety of the interaction, not the degree of automation.
So the front-end ships a "Go to PayPal" + "I paid, capture it" button pair: human authorises, machine executes. That is the correct shape of agentic commerce.
> We deliberately do not automate the browser. Not because it's hard — because the > failure modes are wrong. PayPal's guest checkout treats any non-test email as a new > buyer and walks it through account creation (password → date of birth → ID → > postcode → address verification → SMS code). Sandbox doesn't send SMS, so that path > is a dead end. Using the sandbox buyer account avoids the whole flow. > See [DEMO_SCRIPT.md](file:///D:/paypal-ai-hackathon/DEMO_SCRIPT.mdDEMO_SCRIPT.md for the recorded findings.

The seven-node state machine


NodeRoleAI? |---|---|---| `parse_node`Natural language → structured `PurchaseRequest`✅ LLM function calling `validate_node`Evaluate against the constraint engine❌ deterministic `insight_node`"You've spent $170 of $200 this month; this $10 fits, $20 left"✅ LLM `explain_node`"Blocked: over your $50 threshold — raise it or split the order"✅ LLM `approve_node`Decide AUTO_APPROVE / REQUIRE_HUMAN / REJECT❌ deterministic `pay_node`Create the real sandbox order via PayPal Agent Toolkit❌ `verify_node`Confirm the order state❌
> Hard rule: constraint checking and approval decisions are deterministic code, never > the LLM. The model decides *what the user meant*; the engine decides *whether it's > allowed*. Both AI nodes have pure-template fallbacks, so the demo never breaks even > if the endpoint is down.

LLM endpoint: fully swappable


Intent parsing speaks the standard OpenAI protocol, so any OpenAI-compatible endpoint works — change three environment variables, zero business-code changes.
Endpoint`LLM_BASE_URL``LLM_MODEL` |---|---|---| Z.ai (used here, free tier, overseas sign-up)`https://api.z.ai/api/paas/v4``glm-4.7-flash` Tencent MaaS`https://tokenhub.tencentmaas.com/v1``glm-5.3-flash` DeepSeek`https://api.deepseek.com``deepseek-chat` OpenAI`https://api.openai.com/v1``gpt-4o-mini`
Measured on Z.ai `glm-4.7-flash`: 20 sentences × 3 runs = 60/60 correct, 20/20 stable across runs, 0 silent degradations. The 20-sentence set covers all three decision scenarios plus threshold boundaries ($50 vs $50.01) and two reasoning cases (price comparison across the catalog, and disambiguation by product category).
The expected outcomes are hand-enumerated and frozen in the script's `CASES` table — not model self-assessment, not back-filled after the fact — and the decisions come from the same `evaluate()` the production server uses. Full report: [LLM_INTENT_VERIFICATION.md](file:///D:/paypal-ai-hackathon/LLM_INTENT_VERIFICATION.mdLLM_INTENT_VERIFICATION.md.
Engineering note — free-tier 429s are normal. Free endpoints randomly return `429` with code `1305` (overloaded) or `1302` (rate limited); measured success rate at peak was ~20%. That's endpoint capacity, not a code bug. Three layers handle it: client-side rate limiting (`LLM_MIN_INTERVAL`), exponential backoff with ±30% jitter (8→16→32→45s, 6 attempts), and observable degradation — `agent/llm_intent.py` maintains counters (`calls`/`success`/`rate_limited`/`retries`/`degraded`/`no_tool_call`) so a report can never claim "verified" while the AI path was silently down.

The MCP capability we wired — and why it can't replace REST or the Toolkit


`agent/mcp_client.py` speaks the MCP protocol directly over stdio (JSON-RPC 2.0, newline-delimited JSON) to the official PayPal MCP server (`@paypal/mcp`, run via `npx`). We wired one tool: `invoices.list` — listing invoices is something neither REST Orders v2 nor our Toolkit wrapper covers.
It was verified end-to-end, not just wired: creating an invoice through `invoices.create` returned `INV2-CG5H-58YR-9KCR-VP8P`, and `invoices.list` then returned that same invoice back from PayPal's sandbox.
Why MCP cannot replace the other two paths — and this is a design property, not a preference:
> The official MCP server exposes 28 tools, and many of them move money > directly: `orders.capture`, `payments.createRefund`, `subscriptions.cancel`, > `pay_order`, `invoices.send`, `disputes.create` … > > MCP is a *tool-call protocol* — it executes what the tool says, immediately, > with no policy layer in between. REST and the Toolkit both pass through > MandatePay's `evaluate()` before anything happens.
So an agent given raw MCP access could capture an order or cancel a subscription without the constraint engine ever seeing it — which is precisely the failure mode this project exists to prevent. MandatePay therefore keeps MCP behind a gate (`agent/mcp_guarded.py`):
| REST / Toolkit (our implementation)Raw MCP access |---|---|---| Money movementAlways goes through `evaluate()` firstExecutes directly — bypasses the constraint engine ScopeOnly the operations we implementedAll 28 official tools, including refunds and subscription cancellation Audit trailEvery decision produces Intent/Cart/Payment recordsNo Mandate record is produced
Concretely, `agent/mcp_guarded.py` maintains a read-only allowlist (`invoices.list`) and an explicit money-moving denylist (9 tools, each with the reason it is blocked). A blocked tool is rejected *before* any PayPal API call is made — it never even starts the MCP process.
```bash # See the whole thing work: read-only tool fetches real data, # money-moving tools are blocked before any call is made python scripts/demo_mcp.py ```
> The MCP path needs Node.js 18+ (the official server runs via `npx`). > Everything else in this project is pure Python — the MCP capability is the one > optional extra that pulls in a Node runtime. The Python side is a hand-rolled > stdio JSON-RPC client precisely to avoid adding an MCP SDK dependency to the > deployment (which would slow the build and the cold start). > > The remote PayPal MCP endpoint (`mcp.sandbox.paypal.com`) is not usable > here: it only accepts tokens from its own OAuth authorization-code + PKCE > flow, which needs an interactive browser login. The local stdio server accepts > the ordinary client-credentials token, so that's the path we use.

AG Studio: dashboards defined by code, decisions still in tested code


The `/budget` page is rendered by [AG Studio](MISSING://AG Studiohttps://www.ag-grid.com/ag-studio/ — but with a deliberate split:
1. The dashboard is pre-defined in code. `createStudio()` + `setState()` in `static/budget.html` describe the KPIs, charts and layout programmatically. No one drags widgets in an editor; the dashboard is reviewable in a diff. 2. Rendering and decision-making are separated. AG Studio owns *presentation* — KPI tiles, charts, cross-filtering. The budget arithmetic and every constraint decision stay in our own testable Python. The 650-judgement stress report ([STRESS_REPORT.md](file:///D:/paypal-ai-hackathon/STRESS_REPORT.mdSTRESS_REPORT.md) is the reason we're comfortable doing it that way.
The backend was not modified to adopt AG Studio — `/budget` reads the same `/api/budget/summary` endpoint it always did, and the page shapes the data client-side. AG Studio is an npm commercial product with a 45-day free trial (fully functional, no UI watermark). The page probes for a local runtime and falls back to jsDelivr CDN if it isn't installed — so a fresh clone works with zero extra setup, and if the runtime ever fails to load the page degrades to a hand-built view instead of a blank page.

A real vulnerability we found and fixed


The constraint engine is stress-tested against three independent oracle implementations (a spec-literal one, one reproducing the pre-fix behaviour, and one derived from user intuition) over 50 random constraints × 13 requests = 650 judgements, 550 of them adversarial.
One finding mattered:
> Class F — category allowlist silently skipped when the category is unknown. > 170 of 650 cases (26.15%). When a constraint restricted the allowed *categories* > but the incoming request carried no category field, the category check was skipped > entirely — the constraint was effectively void. A security hole, not a cosmetic one.
The fix: an unknown category with a category allowlist set now returns `REQUIRE_HUMAN` instead of silently passing — not a hard reject (the field is often legitimately absent, and rejecting would break legitimate purchases), but never a silent allow. After the fix: 0 false rejects, 0 false allows.
The other findings were over-strict rejections — `notion` vs `Notion`, a stray space from copy-paste — now fixed by normalising the comparison.
> ⚠️ Precise wording matters here: 26.15% is the pre-fix figure. The > vulnerability is found and closed. This is a closed-loop story, not a live hole. > See [STRESS_REPORT.md](file:///D:/paypal-ai-hackathon/STRESS_REPORT.mdSTRESS_REPORT.md for the full breakdown.
The methodology point worth stealing: the stress test does not use the engine as its own answer key — that would be no test at all. Instead it re-derives every expected verdict from three hand-written oracle implementations, each written against the constraint specification rather than against the engine's code, so they share no evaluation logic with what they are checking:
OracleWhat it encodesWhat it catches |---|---|---| strictthe engine's current specificationwhether the implementation drifted from the spec legacythe pre-fix semanticswhat users had actually been experiencing productwhat a user would reasonably expectthe false rejects and false allows people hit
The cases are randomly generated (50 random constraints × 13 requests = 650, 550 of them adversarial), but the expectations are code, not model output — every oracle is a deterministic function, so a verdict can never be "whatever the model felt like saying". The LLM only ever explains *why* something is a vulnerability; it never enters the decision chain, and it never gets a vote on the verdict.
> This is a different claim from the one in [Intent > verification](MISSING://Intent > verification#llm-endpoint-fully-swappable below, and the distinction matters: > the 20 intent sentences *are* hand-enumerated and frozen in > `scripts/verify_llm_zai.py`'s `CASES` table, because there the question is > "did the LLM parse this correctly?". Here the question is "does the constraint > engine agree with three independent readings of its own spec?" — so the cases > are generated and the expectations are computed.

API authentication


`/api/*` requires a signed session cookie. The page routes are exempt and issue the cookie on visit, so the front-end needs zero changes — same-origin `fetch` carries it automatically.
```bash curl -i https://<host>/api/mandates # → 401 (no cookie) curl -c cookies.txt https://<host>/audit # get a session curl -b cookies.txt https://<host>/api/mandates # → 200 ```
Exempt: the five page routes, `/healthz`, `/api/health`, and `/api/webhook` (PayPal calls that endpoint server-to-server and cannot carry a browser cookie — it has official PayPal signature verification instead). Details: [W08_API_AUTH.md](file:///D:/paypal-ai-hackathon/W08_API_AUTH.mdW08_API_AUTH.md.

Webhook — optional, and the main flow does not depend on it


The webhook is not required. The core demo loop is *"agent orders → human approves on PayPal → click 'I paid, capture it' → the server captures and marks the Mandate COMPLETED."* That works without a webhook.
The webhook exists so that PayPal can *push* status changes (`PAYMENT.CAPTURE.COMPLETED`, `CHECKOUT.ORDER.APPROVED`, `PAYMENT.CAPTURE.DENIED`, `PAYMENT.CAPTURE.PENDING`) instead of the server polling. When configured, `/api/webhook` verifies PayPal's official signature (`PAYPAL-TRANSMISSION-ID` / `-SIG` / `-TIME` / `-CERT-URL` / `-AUTH-ALGO` plus `PAYPAL_WEBHOOK_ID`) against PayPal's own verification endpoint and only then processes the event. Events are stored idempotently by `event_id`.
Skip it if you just want to look around. `python scripts/setup_webhook.py --create --url <your-public-url>/api/webhook --force` registers it if you want the full loop.

Known limitations


Stated plainly, because a demo that oversells itself is worse than one that doesn't.
1. No account system. Any visitor who opens a page gets a session. The goal is to stop casual scripted scraping, not to stop a determined attacker. There is no rate limiting and sessions aren't per-user. This is a demo, not a payment product. 2. The agent cannot complete a payment on its own — by design (see above). 3. AG Studio runs in trial mode (45 days, fully functional, no UI watermark). The page falls back to a hand-built view if the runtime fails to load. 4. Free-tier LLM endpoints are unreliable under load (measured ~20% success at peak). Handled with retries and observable degradation, but it is a real constraint. 5. The LLM is a single point of failure for intent parsing — mitigated by a rule-based fallback, which is why the demo never hard-stops. 6. The MCP integration is minimal — one capability, deliberately, to avoid disturbing the two verified paths.

UI language


The five pages are bilingual, English-first — every visible string carries English, with the Chinese kept alongside it where it helps (this is a Chinese-voiceover demo with English subtitles, so the two are meant to sit together). No visible block is Chinese-only.
Two checks enforce it, and both are cheap to run:
```bash python scripts/check_ui_english.py # static — reads the HTML source python scripts/check_ui_rendered.py # headless Chrome — renders each page and checks the result ```
The second one exists because static analysis misses a real case: Chinese that only appears after JavaScript runs — e.g. AG Studio's KPI labels are pre-defined in `createStudio`/`setState`, not in HTML text nodes, and a `<span>` around the Chinese splits it into a separate text node that looks Chinese-only in the DOM but renders as one bilingual line. Rendering is the only way to be sure.
`python -m pytest tests/test_ui_english.py` runs the static half as part of the normal suite.
